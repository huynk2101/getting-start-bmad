# Accessibility Review — SchoolDesk

## Overall verdict
The spines establish a solid accessibility floor with clear intent and specific WCAG references, but contain a critical contradiction in the badge token spec, a non-compliant timer warning color, and several gaps around exam full-screen mode focus trapping, skeleton loading announcements, and toast auto-dismiss pausing. The exam-taking surface — the most cognitively demanding flow — needs the most reinforcement.

## Findings by category

### Color Contrast — broken
- **critical** Badge token mismatch — DESIGN.md frontmatter defines all three badges as white-on-color (e.g. `badge-pending: foreground #FFFFFF on warning #9E8A5A`), but the component spec at line 168–173 defines tinted-background badges with dark text. These are two different implementations. If anyone implements from the frontmatter tokens, white-on-warning yields ~2.7:1 — a WCAG failure. (DESIGN.md:63–74 vs 168–173). *Fix:* Delete or correct the frontmatter badge tokens to match the tinted-background spec; remove the contradictory `foreground: '#FFFFFF'` entries.
- **high** Timer warning color `#9E6A6A` on exam-surface `#F5F2ED` yields ~4.37:1 — fails AA 4.5:1 for the 20px Georgia text used in the timer. (DESIGN.md:199–201). *Fix:* Darken danger to `#8E5555` or use `#7A4A4A` to reach 4.5:1+, or document the timer as large text (≥18.66px bold / 24px) to qualify for the 3:1 threshold — but 20px weight-400 Georgia does not qualify as "large text" under WCAG.
- **medium** `text-muted` (#7A7A7A) on `surface` (#FFFFFF) yields ~4.48:1 — technically passes AA for normal text, but is borderline and may fail on low-quality displays or with anti-aliasing differences. Used for timestamps, meta lines, table headers. (DESIGN.md:103). *Fix:* Darken to `#767676` (the classic AA floor) or `#707070` for safety margin.
- **low** Accent border color `#9B7E5A` on white surface yields ~2.15:1 — fails non-text contrast for UI components, but is purely decorative (left-border stripe on callout notes). Acceptable as decorative, but if ever repurposed as an interactive indicator, it will fail. (DESIGN.md:98). *Fix:* Document explicitly that accent is decorative-only and must never be used for interactive state indicators.

### Keyboard Navigation — adequate
- **high** Exam full-screen mode uses `Escape` to exit with confirmation dialog, but no focus-trap mechanism is specified. A keyboard user could Tab out of the exam into browser chrome or background page content during the exam. (EXPERIENCE.md:102, 128). *Fix:* Specify `focus-trap` on the exam-taking container: cycle Tab within the exam surface, and only release focus on confirmed exit.
- **high** Arrow key navigation for exam questions is specified, but the relationship between question navigation sidebar and main question content is undefined. Arrow keys in the sidebar vs. in the question area may conflict. (EXPERIENCE.md:103). *Fix:* Define two focus zones: arrow keys navigate questions only within the sidebar list; once focus is in the question body (answer options), arrow keys operate radio buttons. Tab moves between zones.
- **medium** Grading table inline editing specifies Enter saves and moves to next input, but does not specify what happens on Escape within a score input — can the teacher cancel an in-progress edit? (EXPERIENCE.md:104). *Fix:* Define Escape behavior: revert to previous value and move focus to the row action area.
- **medium** Toast dismiss via Escape is specified, but toasts auto-dismiss after 3–4 seconds. No mechanism to pause auto-dismiss on keyboard focus or hover. A keyboard user navigating to a toast may not reach it before it vanishes. (EXPERIENCE.md:102, EXPERIENCE.md:76). *Fix:* Pause auto-dismiss while toast has focus; resume on blur or after extended timeout (10s).
- **low** Hamburger menu at `sm` breakpoint — no specification of keyboard activation or focus management when menu opens/closes. (EXPERIENCE.md:140). *Fix:* Specify: Escape closes menu, focus returns to hamburger button, Tab is trapped within open menu.

### Screen Reader Support — thin
- **high** `role="application"` on the exam-taking interface suppresses standard screen reader keyboard shortcuts and mode switching. This is a well-known anti-pattern unless the interface genuinely requires custom keyboard handling (like a rich editor). An exam with radio buttons and navigation does not justify `role="application"`. (EXPERIENCE.md:127). *Fix:* Remove `role="application"`. Use standard landmarks, heading hierarchy, and ARIA attributes instead. Screen reader users need standard browse mode to read question text.
- **high** Skeleton loading states are described as "animated gray bars" with no screen reader announcement. Users who cannot see the shimmer will encounter an empty or partially-rendered page with no indication that content is loading. (EXPERIENCE.md:84, DESIGN.md:177). *Fix:* Add `aria-busy="true"` and `aria-live="polite"` on skeleton containers; announce "Loading your classes" or similar on mount; announce "Loaded" on resolution.
- **medium** Progress bar has `aria-valuenow/min/max` specified, but the milestone messages ("Halfway there!", "Just 5 more!") are not specified as `aria-live` announcements. (EXPERIENCE.md:72, 174). *Fix:* Announce milestones via `aria-live="polite"` when progress crosses 50%, 75%, 90%, 100% thresholds.
- **medium** Auto-save checkmark indicator on exam questions — visual only, no screen reader announcement specified. (EXPERIENCE.md:173). *Fix:* Use `aria-label="Question 1, answered"` on the question container, or add a visually-hidden status text "Saved" that is announced on each auto-save.
- **medium** Table column headers need `<th scope="col">` and row headers `<th scope="row">` explicitly called out. The spine says "semantic HTML for tables" but does not specify scope attributes. (EXPERIENCE.md:126). *Fix:* Add `<th scope="col">` for grading table column headers (Name, Score, Status, Actions) and `<th scope="row">` for student names.
- **low** Timer color change (green → amber → red) is purely visual. Screen reader users receive the 60-second interval announcement, but the color transition at 5 minutes and 1 minute is not announced. (EXPERIENCE.md:175). *Fix:* Announce "5 minutes remaining — time is running low" and "1 minute remaining" via `aria-live` at those thresholds.

### Focus Management — thin
- **high** No focus-management specification after modal open/close (Finalize Grades confirmation dialog). Focus should move to the dialog on open and return to the trigger button on close. (EXPERIENCE.md:78). *Fix:* Specify: on Confirm dialog open, focus moves to the Cancel button (safest default); on close (confirm or cancel), focus returns to the "Finalize Grades" button.
- **high** Exam submission: focus behavior after "All done, Alex!" toast and redirect to Results is undefined. The user may lose orientation. (EXPERIENCE.md:177). *Fix:* After redirect to Results, move focus to the page heading ("Biology Midterm — Your Results") and announce it.
- **medium** Toast dismiss behavior: no specification of where focus goes after a toast is dismissed (auto or manual). If focus was on the toast, it should return to the previously focused element. (EXPERIENCE.md:76). *Fix:* On toast dismiss, return focus to the element that was focused before the toast appeared (save focus context on toast mount).
- **medium** Error inline banner: no specification that focus moves to the error on appearance. For auto-save failures in the grading table, the teacher needs to know the error exists. (EXPERIENCE.md:167). *Fix:* Add `role="alert"` or use `aria-live="assertive"` (already specified), and optionally move focus to the error banner on appearance for critical errors.
- **low** Navigation between surfaces (e.g. clicking "Exams" in top nav) — no focus management specified. Best practice: move focus to the new page heading on route change. (EXPERIENCE.md:132 partially addresses: "Tab order matches visual reading order"). *Fix:* On route change, move focus to `<h1>` or main content landmark.

### Motion & Animation — adequate
- **medium** `prefers-reduced-motion` is addressed (EXPERIENCE.md:131), which is good. However, the skeleton shimmer animation is described as "pulse or shimmer" (DESIGN.md:177) and the exam fade-in is a CSS transition (EXPERIENCE.md:110). The reduced-motion spec says "content appears instantly" — but does not address whether skeletons resolve to their final state or just appear without animation. Clarify: skeletons should be replaced by loaded content (not hidden). (DESIGN.md:177, EXPERIENCE.md:131). *Fix:* Specify: with `prefers-reduced-motion`, skeletons are replaced by loaded content immediately (no shimmer, no fade-in transition).
- **low** Toast dismiss animation — not explicitly listed in the reduced-motion override. (EXPERIENCE.md:131). *Fix:* Add toast dismiss to the reduced-motion list.

### Touch Targets — adequate
- **medium** Button padding at default is `6px 14px` and `btn-sm` is `4px 10px` with 12px label font. At `sm` breakpoints, `btn-sm` renders a total touch target well below 44×44px (roughly ~28px tall with 4px vertical padding + 12px font). (DESIGN.md:160). *Fix:* At `sm` breakpoints, enforce minimum 44×44px touch targets on all interactive elements. Add to responsive spec.
- **medium** Badge padding is `3px 10px` at 11px font — approximately 17px tall. Badges are non-interactive (status indicators), so this is acceptable under WCAG 2.5.8 (target size). But if any badge becomes clickable in a future iteration, it will fail. (DESIGN.md:168). *Fix:* Document that badges are informational only and must never become interactive without resizing to 44×44px.
- **low** Grading table inline score inputs — small by design for density. At `sm` breakpoint they stack to one student at a time, which mitigates the issue. (EXPERIENCE.md:140). *Fix:* Verify at `sm` that stacked score inputs meet 44×44px minimum.

### Error Identification — adequate
- **medium** Errors use inline banners (not modals), which is good. The spine specifies `aria-live="assertive"` for errors (EXPERIENCE.md:130). However, the error message text does not explicitly associate the error with the specific form field or student row in the grading table. (EXPERIENCE.md:167). *Fix:* For grading table errors, add `aria-describedby` on the score input pointing to the error message, or use `aria-errormessage`.
- **medium** Login error message ("Invalid credentials") is mentioned in the PRD (FR-23) but not in the UX spine. No specification of how login errors are announced or positioned. (PRD:304, EXPERIENCE.md — absent). *Fix:* Add login error pattern: inline below the form, `role="alert"`, focus moves to error on failed submit.
- **low** Exam conflict warnings are inline banners (good — not modals). But no specification that these are announced on appearance. (EXPERIENCE.md:94). *Fix:* Add `aria-live="assertive"` to exam conflict inline warnings.

### Language & Semantics — thin
- **medium** No mention of `lang` attribute on the HTML element or any multilingual considerations. If the school serves multilingual students or the UI is ever localized, this is required. (Neither file). *Fix:* Specify `lang="en"` on `<html>` (or appropriate locale). If localization is planned, note that `lang` attribute must change per-user.
- **low** Heading hierarchy is implied by typographic tokens (display = h1, display-sm = h2/h3) but not explicitly specified in the experience spine. (DESIGN.md:112–114, EXPERIENCE.md). *Fix:* Add to Accessibility Floor: "Heading hierarchy is h1 → h2 → h3, never skipped. Each surface has exactly one h1."
- **low** Landmark structure (nav, main, aside) is not explicitly specified. The spine mentions "sidebar" and "top nav" but does not map them to landmark roles. (EXPERIENCE.md:17). *Fix:* Specify: top nav = `<nav aria-label="Primary">`, main content = `<main>`, sidebar = `<nav aria-label="Secondary">` (if retained at lg).

### Exam-Taking Accessibility — broken
- **high** Full-screen mode: no specification of how full-screen is implemented. If using the Fullscreen API, screen reader behavior is inconsistent across browsers. If using CSS full-viewport overlay, focus trapping must be explicit. Neither is specified. (EXPERIENCE.md:40, 110). *Fix:* Specify implementation approach. If CSS overlay: apply `inert` to background content, trap focus within exam container. If Fullscreen API: document that screen reader support varies and provide a non-fullscreen fallback.
- **high** Exam auto-submit on timer expiry: no specification of what happens to focus or how the student is notified. The exam just "submits whatever was answered." A keyboard or screen reader user may not realize the exam ended. (PRD:266, EXPERIENCE.md:175). *Fix:* On auto-submit: announce "Time is up. Your exam has been submitted." via `aria-live="assertive"`, move focus to the results redirect heading.
- **high** Question navigation sidebar: no ARIA roles specified. Is it a list? A tablist? A navigation landmark? Screen readers need structure to navigate between questions. (EXPERIENCE.md:103, 174). *Fix:* Use `<nav aria-label="Question navigation">` with `<ol>` list items; mark current question with `aria-current="true"`; answered questions with `aria-label="Question 1, answered"`.
- **medium** Radio button answer selection: no specification of how the selected state is communicated beyond the visual checkmark. Standard radio button semantics should be sufficient, but the spine does not confirm that standard `<input type="radio">` with `<label>` elements are used (vs. custom div-based radios). (EXPERIENCE.md:173). *Fix:* Specify: use native `<input type="radio" name="q1">` with associated `<label>` elements. Do not use custom div-based radio buttons.
- **medium** Exam confirmation dialog ("Submit your exam? You've answered 28 of 30 questions") — no specification that unanswered questions are listed or that the dialog is keyboard-navigable with focus trap. (EXPERIENCE.md:176). *Fix:* Add focus trap to confirmation dialog. List unanswered question numbers in the dialog text for cognitive clarity.
- **medium** Timer `aria-live="polite"` at 60-second intervals may be too infrequent. If a student is deeply focused, they may miss the "5 minutes remaining" announcement if it fires during a `polite` queue behind other content. (EXPERIENCE.md:129). *Fix:* At 5 minutes and 1 minute remaining, use `aria-live="assertive"` to ensure the announcement cuts through.
- **low** Offline warning during exam: inline banner, no modal (good). But no screen reader announcement specified for the offline state transition. (EXPERIENCE.md:179). *Fix:* Add `role="alert"` to the offline warning banner.

## Summary
- Critical: 1 (badge token contradiction — will produce AA failures if implemented from frontmatter)
- High: 8 (timer contrast, focus trap missing, `role="application"` anti-pattern, skeleton loading silent, modal focus management, exam full-screen implementation, exam auto-submit feedback, question sidebar ARIA)
- Medium: 11 (muted text borderline, grading escape, toast pause, progress milestones, auto-save announcement, table scope, error association, login errors, lang attribute, radio button spec, exam confirmation dialog)
- Low: 6 (accent border, hamburger menu, toast animation, badge touch target, heading hierarchy, landmark structure, offline alert)
